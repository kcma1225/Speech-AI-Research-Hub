# 核心鐵律（跨所有文件類型適用）

來源：Lab-Hub repo 的 `CLAUDE.md`、`README.md`、`conventions/*.md`，以及各 `guides/*.md` 重複出現的規則。這份是彙整，個別站的細節以該站 reference 為準。

## 1. 工具只能是 Quarto

- 所有「給教授看」或「給產業方看」的報告，一律 `.qmd` → render 成 `.html`（reveal.js），不是 PPT、Keynote、Google Slides。
- `.html` 跟著 `.qmd` 一起 commit 進 repo（教授直接開瀏覽器看，不必自己 render）。
- 演講稿寫在 `::: {.notes}` 區塊，簡報時按 `S` 看。
- 固定 YAML（1280×800、KaTeX 數學、MathML presenter-view 修正腳本）——不要自己改版面或加主題；**不要美化，時間花在內容上**。
- render 指令：`quarto render <path>.qmd`。

## 2. AI 禁寫頁（依文件類型，务必查對應 reference 的精確頁碼）

| 文件類型 | 使用者必須自己寫的部分 |
|---|---|
| 論文報告投影片（13 頁） | 第 7 頁（走線講稿）、第 12 頁（我的判斷）、第 13 頁（啟發） |
| idea card | 不能把 AI 生成的 idea 直接當 card 呈報；痛點證據、prior work 比對、「我為什麼之前沒看到」必須使用者自己判斷 |
| 實驗設計（第 2 站） | 一頁決策紀錄的「一句話主張」與審核欄位；Table 1 砍不砍格由教授決定 |
| 復現與紀錄 | 錯誤分析的人工聽樣／標註結論；降 baseline 與否由教授決定 |
| 審稿對帳 | 「想到了嗎」「類別」的判斷 |
| 產學需求規格表 | 門檻數字（由教授與產業方定，不是 AI 猜） |

這些欄位留 `〔〕`，並在交付前明確告知使用者：「這幾格要你自己寫，AI 不能代填」。

## 3. 語言規則

| 文件類型 | 投影片本體 | 講稿/正文 |
|---|---|---|
| 進度報告（第 5 站） | 中文可 | 中文 |
| 論文報告投影片 | **一律英文**（標題、圖說、表格、條列） | 繁體中文（臺灣用語），專有名詞留英文 |
| Deep Research 報告 | — | 繁體中文輸出，但搜尋來源要求英文 |
| 設計文件、核對紀錄、idea card、日誌 | — | 繁體中文 |
| 產學雙週報告 | 中文，專有名詞留英文 | 中文 |

## 4. 來源標記制度

凡是 AI 協助生成、使用者核對過、或使用者自己寫的內容，一律標記來源：

- `AI` — AI 生成尚未核對
- `AI→✓` — AI 生成、已核對過（註明對回原始出處：論文表號/章節、results.csv 的 run_id 等）
- `我` — 使用者自己寫，不假手 AI

這個標記制度明確出現在論文報告的核對紀錄表，但精神適用所有文件：**任何呈給教授的數字或結論，都要說得出它從哪裡來、誰核對過**。

## 5. 教授專屬決定權

以下事項 AI 與 skill 都不能代答，只能幫使用者把問題帶到教授面前（見 `references/ask-professor-index.md`）：
題目、資料集、GPU 資源、目標會議與截稿日、baseline 降不降層、Table 1 砍不砍格、idea card 過不過、審核紀錄要不要退回；
產學分支另加：需求變更接不接、交付內容、發表限制三件（能不能投、投稿前給產業方看多久、產業方資料能不能寫進論文）。

遇到這些問題，模板留白寫「待教授決定／待教授確認」，不要自己填一個合理猜測進去。

## 6. Mermaid 圖規則

- 畫圖前先用文字列出節點與邊，再轉 Mermaid。
- 節點標籤**不能含括號、引號、斜線**（會讓語法壞掉）。
- 架構圖如果是論文報告第 4/5/6 頁的訓練/推論三連圖，三張圖的節點命名要完全一致（同一張圖改三次）。
- 新增/修改的模組用加粗邊框 `stroke-width:4px` 標示；凍結模組用灰底 `fill:#ddd` 標示。

## 7. 審核/確認紀錄只能累加，不能覆蓋

- 設計文件的「審核紀錄」、需求規格表的「確認紀錄」、idea log 的「狀態欄」都是**歷史軌跡**：新決定用新的一行/新版本號記錄，舊版留著，不覆蓋。
- 改版要加版本號（v1 → v2），舊版保留在檔案或獨立存檔。

## 8. 核對義務，不是選讀

每份 reference 底部都有一節「怎麼核對」——這是交付前的強制檢查清單，不是參考性質。skill 執行時最後一步務必照單打勾，缺一項要明確告知使用者「這項還沒核對」。

## 9. GitHub Issue / repo 慣例（進度報告、產學雙週報告適用）

- 進度報告：repo 開 Issue，標題 `〔YYMMDD〕 進度`，label `progress`；教授回饋**當場**記錄在 Issue 留言，不要會後憑記憶補；下週報告第一行引用上週 Issue 連結。
- 產學雙週報告：報告後寫會後紀錄 `minutes_〔YYMMDD〕.md`，需求變更一律標「待教授確認」。
- `results.csv`／`acceptance.csv` 是唯一事實來源，投影片任何數字要對得回其中一列。
